# Visual plan: one self-contained HTML file

> Combines Ryan Lisse's `visualize-html-artifacts` workflow with structure adapted from display-dev/visualize (MIT, Copyright (c) 2026 display.dev) and the "smallest view that makes the point" rule from HumanLayer's `show-me` (MIT, Copyright (c) 2026 HumanLayer). Modified for this pack; see [ATTRIBUTION.md](https://github.com/RyanLisse/claude-code-skills-pack/blob/main/ATTRIBUTION.md) and [NOTICE](https://github.com/RyanLisse/claude-code-skills-pack/blob/main/NOTICE).

Make one HTML file that helps a specific reader decide or act on a specific source. Structure first, decoration last.

Request: $ARGUMENTS

## Files in this skill

- [`references/kinds.md`](references/kinds.md): section structure and failure modes for each kind. Read the part for the kind you picked.
- [`assets/skeleton.html`](assets/skeleton.html): starting file with light/dark tokens, metadata, table and diff examples, plus figure CSS. Copy it, then cut what you don't use.

## 1. Pick the kind

| Kind | Source | Reader question |
|---|---|---|
| `plan` | `plan.md`, a spec, chat decisions | What will change, in what order, how do we know it worked? |
| `review` | someone's plan | Is this plan ready, and what must change first? |
| `diff` | branch diff or PR (`git diff`, `gh pr diff <n>`) | What changed, where is the risk, what should I look at? |
| `recap` | merged PRs, `PROGRESS.md`, a sprint | What shipped, what was skipped or shifted, what did we learn? |

With no arguments, infer the kind and source from the conversation (an open `plan.md`, the current branch diff); if that is ambiguous, ask which one. If none fits, say so and suggest plain Markdown. If the source is too vague to name target files, checks or owners, ask instead of inventing them.

## 2. Gather facts, not vibes

- Read the whole source. For `diff`, read the full diff plus enough surrounding code to explain behavior; for `recap`, use `git log`, `gh pr list --state merged` or `PROGRESS.md`.
- Every file, step, risk, owner and number in the page must come from the source or the repo. Mark unknowns as **Open question** in the page.
- Look for brand context: `DESIGN.md`, `tokens.css`, or the project's main stylesheet. Named fonts and palette lead; otherwise keep the skeleton's neutral tokens and say so once.

## 3. Shape check (one message, then wait)

Before writing HTML, send a short outline: the sections with the question each answers, which primitives you will use (table, diff block, diagram) and why, and the output path. Ask one question: "Build it?" Skip this only when the user already gave the structure or said "just build it".

## 4. Build

- One `.html` file, inline CSS, inline SVG, no network requests, no CDN scripts, no web fonts by URL. It must work offline from `file://`.
- Default path: `docs/visual/YYYY-MM-DD-<kind>-<slug>.html` (or the folder the user named). Do not overwrite an existing file without asking.
- Lead with the answer: title, one-sentence thesis, labeled metadata (`Status / Draft`, `Branch / feat/x`, `Updated / 20 Oct 2026`).
- Pick the smallest view per section: a sentence, a list, a table for comparison, a `diff` block for changed shape, a diagram only for relationships prose can't carry. For diagrams, follow `/diagram` (inline SVG, Mermaid only to compute layout, never shipped as a runtime).
- Status and diff colors are never the only signal: keep `+`/`-` markers and text labels.

## 5. Bans (rewrite on sight)

Gradient text; thick left-border callouts; three or four identical icon cards; hero metric tiles ("10x"); icons on every heading; slogans ("Ship faster. Build smarter."); "Generated by AI" or "Hope this helps" footers; big radius plus heavy shadow on ordinary boxes.

## 6. Verify, then deliver

- No external requests: `grep -nEi "(src|srcset|href|poster|action|data)[[:space:]]*=[[:space:]]*[\"']?(https?:)?//|@import|url\([[:space:]]*[\"']?(https?:)?//" <file>` may only match plain `<a href>` links the reader clicks. Any `src`, stylesheet, `@import` or `url(...)` hit is a network dependency: inline it or drop it.
- Check desktop and ~390px width, light and dark (`prefers-color-scheme`). If a browser tool is available, screenshot both; otherwise state that it was not rendered.
- Headings in order, text contrast AA, `<title>` set, tables have captions, SVG has `<title>`/`<desc>`.
- Counts match: tallies equal the items listed; an `on track` status never sits beside an unmitigated high risk.
- Deliver: the file path, how to open it (`open <file>` on macOS, `xdg-open` on Linux), and one line on what the page shows. Offer to commit it only if the user asked for that.

## Refine an existing page

When the user asks to change an existing page, edit it in place with a targeted diff (simplify, quieter, bolder, polish, or review-only findings). If the change would rewrite more than ~40% of the file, propose a rebuild instead.
